# Intelligent Document Analysis — Phase 2 Final Technical Report

## 1. Overview

Phase 2 establishes the annotation and entity-extraction foundation for structured information extraction from processed document chunks.

The objective was to build a reproducible baseline for annotation, extraction, evaluation, and error analysis rather than a production-level NER system.

The workflow is:

```text
Processed Document Chunks
        ↓
Deterministic Sampling
        ↓
Weak Annotation
        ↓
Validation & Analysis
        ↓
Train / Validation / Test Split
        ↓
NER Baseline
        ↓
Hybrid Entity Extraction
        ↓
Structured Predictions
        ↓
Evaluation & Error Analysis
```

The extraction architecture combines deterministic rule-based extraction with a pretrained NER model. Both produce a common `ExtractedEntity` representation and are combined using explicit duplicate and overlap-handling rules.

An important methodological conclusion from Phase 2 is that evaluation quality depends not only on the extraction system but also on the quality and completeness of the reference annotations. The current benchmark is therefore a reproducible development baseline, not independent human-verified ground truth.

---

## 2. Entity Schema

The common entity representation is:

```python
@dataclass
class ExtractedEntity:

    text: str
    label: str
    start: int
    end: int
    confidence: float | None
    chunk_id: str
    document_id: str
    page_start: int
    page_end: int
```

It preserves the entity text, label, character span, confidence, and source-document context.

An `ExtractedEntity` represents an individual occurrence. Identical text appearing at different character spans can therefore represent separate entities.

The deterministic annotation layer generates:

```text
DATE
MONEY
PERCENTAGE
ORGANIZATION
PRODUCT
```

NER labels are mapped into the project schema:

```text
PER → PERSON
ORG → ORGANIZATION
LOC → LOCATION
```

The Hybrid extraction system therefore supports:

```text
PERSON
ORGANIZATION
LOCATION
DATE
MONEY
PERCENTAGE
PRODUCT
```

The weak-annotation benchmark itself contains only the five labels generated by the deterministic annotation layer.

`AutomaticAnnotator` combines regular-expression rules with predefined dictionaries.

### Regex-based extraction

Structured entity types include:

```text
DATE

PERCENTAGE
```

Examples include dates, monetary values, and percentages such as:

```text
2025

```

### Dictionary-based extraction

Predefined dictionaries identify known organizations and products.

Example organization entries include:

```text
Microsoft
Microsoft Corporation
OpenAI
SEC
```

Example product entries include:

```text
Microsoft 365
Azure
Windows
LinkedIn
GitHub
Xbox
Office
Teams
```

The deterministic annotator assigns rule-system confidence values:

| Entity Type  | Confidence |
| ------------ | ---------: |
| DATE         |       0.99 |
| MONEY        |       0.99 |
| PERCENTAGE   |       0.99 |
| ORGANIZATION |       0.90 |
| PRODUCT      |       0.95 |

These values are heuristic assignments, not statistically calibrated probabilities.

The resulting annotations are therefore **weak labels generated by deterministic heuristics**, rather than human-confirmed entity annotations.

## 7. Entity Evaluation Framework

The reusable evaluator is implemented in:

[`src/annotation/evaluator.py`](../src/annotation/evaluator.py)

It calculates:

```text
True Positives
False Positives
False Negatives
Precision
Recall
F1
```

Metrics can also be calculated per entity type.

The main strict evaluator matches entity occurrences using:

```text
(text, label, start, end)
```

Therefore, character span and exact entity text are part of the match. Case differences are not automatically ignored by the strict evaluator.

Some exploratory NER candidate comparisons use normalized `(text, label)` matching. Those results should therefore be distinguished from the strict entity-level evaluation.

The evaluator focuses on TP, FP, and FN because this is an entity-extraction task rather than classification of every token or character position.

## 9. Hybrid Entity Extraction

The Hybrid architecture combines deterministic extraction with contextual NER:

```text
Document Chunks
      │
      ├───────────────┐
      ▼               ▼
Rule-Based        Pretrained
Extraction             NER
      │               │
      └───────┬───────┘
              ▼
      Hybrid Extraction
              │
              ▼
      Extracted Entities
```

The main abstraction is implemented in:

[`src/extraction/entity_extractor.py`](../src/extraction/entity_extractor.py)

The extractor combines:

```text
AutomaticAnnotator
        +
NERModel
        ↓
ExtractedEntity
```

Deterministic extraction provides strong coverage for structured patterns and configured vocabulary, while NER provides contextual recognition of entities such as people and locations.

The rest of the application therefore interacts with a unified extraction interface rather than individual extraction mechanisms.

## 10. Entity Merging and Conflict Handling

The Hybrid extractor applies deterministic rules when combining predictions.

### Exact duplicates

If both systems produce the same entity span and label, only one occurrence is retained.

### Non-overlapping entities

Different valid entities are retained even when only one extraction source identifies each:

```text
Azure      → PRODUCT
Microsoft  → ORGANIZATION
```

### Overlapping entities

The current priority rule preserves overlapping deterministic entities for:

```text
DATE
MONEY
PERCENTAGE
PRODUCT
```

For overlaps involving other rule-based entities, the NER entity may replace the existing overlapping entity according to the implemented conflict rules.

The final entity list is sorted by character position.

These rules provide deterministic engineering behavior; they do not imply that one extraction source is always semantically correct in an overlap.

## 12. Evaluation Methodology and Results

The current evaluation compares:

```text
Rule-Based
NER
Hybrid
```

using the 75-chunk test split.

The selected NER model is:

```text
musk1209/finsight-ner
```

The strict evaluator uses entity text, label, and character span.

The central methodological limitation is that the reference annotations were generated automatically using the same deterministic annotation framework that forms part of the rule-based extraction system.

Therefore, the benchmark primarily measures **agreement with the available weak reference**.

For example:

```text
Source text:
Apple
Microsoft

Weak reference:
Apple → ORGANIZATION

Prediction:
Apple     → ORGANIZATION
Microsoft → ORGANIZATION
```

Strict evaluation produces:

```text
Apple     → TP
Microsoft → FP
```

However, the `Microsoft` prediction may be semantically valid even though it is absent from the weak reference.

Conversely, a valid entity that is absent from the reference cannot be counted as a true positive.

Therefore:

```text
Strict-evaluation False Positive
            ≠
Confirmed semantic error
```

This does not make the Precision, Recall, or F1 calculations mathematically incorrect. It limits what conclusions can be drawn from them.

Rule-based extraction can also obtain very high agreement with the weak reference because the same deterministic rules contribute to both annotation and extraction. Such agreement demonstrates deterministic consistency rather than perfect real-world semantic extraction.

The current benchmark should therefore be interpreted as a **development and regression baseline**, not as human-verified semantic ground truth.

## 13. Error Analysis

Error analysis examines:

* expected entities;
* predicted entities;
* false positives;
* false negatives;
* labels;
* character offsets;
* confidence;
* source context.

Several recurring patterns were observed.

### NER overprediction

NER can identify geographic or organizational expressions that are absent from the weak annotations, including examples such as:

```text
Ireland
Singapore
Japan
India
Australia
Europe
North America
```

Some of these predictions may be supported by the source text despite being absent from the reference.

### Boundary and label differences

Predictions may differ from the weak reference in entity boundaries or labels.

For example:

```text
Reference:  Xbox
Prediction: xbox live → ORGANIZATION
```

or:

```text
Reference:  Office
Prediction: office 365 → ORGANIZATION
```

### Tokenization artifacts

NER can produce subword fragments such as:

```text
cop   → ORGANIZATION
##ilo → ORGANIZATION
```

instead of the intended entity:

```text
Copilot
```

### Low-confidence predictions

Some predictions have low model confidence and may represent extraction noise:

```text
x        → ORGANIZATION   0.5190
outlook. → ORGANIZATION   0.5417
i        → ORGANIZATION   0.6438
```

Confidence filtering may remove some obvious noise, but it cannot solve the broader reference-coverage problem.

The analysis therefore distinguishes genuine extraction errors from cases caused by incomplete references, label differences, boundary differences, or model tokenization.

## 14. Evaluation Limitations and Future Methodology

The main limitation is the absence of an independently verified, exhaustive reference dataset.

A stronger evaluation should follow:

```text
Define Target Entity Schema
        ↓
Create / Correct Annotations
        ↓
Human Verification
        ↓
Train / Validation / Test Dataset
        ↓
Fine-Tune NER
        ↓
Validation-Based Model Selection
        ↓
Final Evaluation on Untouched Test Set
        ↓
Independent Error Analysis
```

The existing 350/75/75 split can support this workflow:

```text
350 Training
75 Validation
75 Test
```

The intended process is:

1. Fine-tune the NER model on the 350 training chunks.
2. Use the 75 validation chunks for model and configuration selection.
3. Keep the 75 test chunks untouched until final evaluation.
4. Filter predictions according to the explicitly defined project target schema.
5. Compare predictions against complete human-verified entity annotations.
6. Preserve schema-valid predictions even when their specific entity value is absent from the reference.
7. Count unmatched valid predictions as false positives.
8. Count reference entities not predicted as false negatives.
9. Report Precision, Recall, and F1 together with qualitative error analysis.

The key principle is that predictions should be filtered by the **target schema**, not by whether their specific values already appear in the reference annotations.

## 15. Future Human-Verified Evaluation

A stronger benchmark does not necessarily require annotating the entire document collection.

A smaller, carefully reviewed dataset can provide a more meaningful evaluation reference:

```text
Weak Automatic Annotation
        ↓
Manual Review / Correction
        ↓
Human-Verified Reference Dataset
        ↓
Model Development
        ↓
Held-Out Human-Verified Test Set
```

This would allow future Precision, Recall, and F1 results to be interpreted as measurements against a more credible reference standard.

The Hybrid system can then be evaluated using the same reference while keeping extraction architecture and evaluation methodology separate.

The intended Hybrid workflow is:

```text
Rule-Based Extraction
        +
Fine-Tuned NER
        ↓
Schema Filtering
        ↓
Duplicate Removal
        ↓
Explicit Conflict Handling
        ↓
Final Entity Set
        ↓
Evaluation Against Verified Reference
```

Exact duplicate occurrences should be removed only when they represent the same entity span and label within the same chunk. Different valid predictions should remain available for evaluation.

The most important methodological result is that the current metrics measure agreement with an automatically generated reference more directly than independent semantic correctness. The next meaningful iteration is therefore:

```text
Define Target Schema
        ↓

        ↓
Select Using Validation Data
        ↓
Evaluate on Untouched Test Data
        ↓

        ↓
Independent Error Analysis
```

Phase 2 is complete as a **baseline annotation, hybrid extraction, evaluation, and error-analysis implementation**. Further improvements should focus on reference quality and project-specific evaluation rather than adding unnecessary extraction complexity.
